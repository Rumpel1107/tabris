## Notes

- **What answers DEF-15 for instructions already stored is slice 6 (slice 7 for mixed rows), not slice 3.** Slices 1 to 3 protect an instruction saved from then on; one already living as a fact — the owner's own, the daily report's among them — stays exposed to a merge until the review moves it. That is why the review comes right after the proposal cycle it stands on, and before changing an instruction, which it does not need. Reordered on 2026-10-01: until then the review came eighth, and the notes claimed the fifth slice answered DEF-15 while the owner's own orders were still facts.
- **The distillation's creation and its notice ship together, last.** An instruction created in the background changes how Tabris answers, so it is never created in production before the user can be told (spec question 6). Slice 9 is verified in the CLI against the development database and deployed with slice 10; until then the distillation behaves as today and may keep a new instruction as a fact, which a review moves later. The notice can promise both changing and removing because slices 5 and 8 exist by then.
- **Slice 1 touches no row that already exists.** Until 2026-10-01 it did: a new counter table changed how `save_fact` numbered facts and had to be seeded from production's real maximum. Plan D13 replaced it with the facts table's own counter, which survives a rollback to an earlier tag and leaves `save_fact` as it is. Without that table the slice is estimated at about 160 hand-written lines, tests included, so no split is planned; the recital is what calls the store, so the two could not be shipped apart anyway.
- **Slice 2 measures before it builds, and so does slice 3.** The plan's own risk section says F1 and F2 recognition is unmeasured: the probe measured the review of stored rows, not the turn. Slice 3's probe is the one that can change the plan — if the `general` roster rarely calls `save_instruction` on real instruction-shaped messages, F1 shrinks to what slice 9's distillation catches, and the announcement of slice 10 becomes the main way a user learns anything was saved. That is why the two probes come before their code and not after.
- **Slice 5 measures before it builds, like 2 and 3.** Its probe says how often a reply is read as agreement when it was not — the cost the owner accepted in plan D12 — and it is the machinery slices 6 to 8 stand on, so a poor number changes those three, not the four before. Slice 4, the proposal and its lapse, was split from it on 2026-10-01 to keep each under 200 lines; it is verified in the CLI and reaches production with slice 5. A buttons slice stood in that place until the same day; plan D12 removed it.
- **Slices 6 and 7 are split on the mixed rows on purpose.** The whole-row copy is exact and needs no model beyond the classification; the split needs a second call and is the one place a part can be dropped. Keeping them apart means the owner can move his four instruction rows without exposing the four mixed ones to a split in the same change.
- `probe_kind.py` is not committed: it lives in a session scratchpad outside the repository, which is cleared without notice. Slice 6 is what gives it a home in `tools/`, beside `probe_freshness.py`; slice 3 needs it earlier, so slice 3 is what commits it — a measured prompt that exists only in a temporary directory cannot be the one production runs.
- **The sample messages in these rows are in Spanish because that is how the owner exercises the app; each one that becomes a test, a probe case or an example in a tool description carries its English twin** (`CONTRIBUTING.md`, examples come in both languages). English is the default language, and a set of examples in one language leaves the other unexercised. Slices 4 and 5 already name their English cases; the others gain theirs when they are built.
- **Read against the other phase documents.** The spec's twelve acceptance criteria all have a slice, and the plan's coverage table is the map this list follows. Three things the spec resolved are deliberately absent from every slice: a cap on how many instructions a user may hold (question 7, deferred — what ships is the count and the warning of slice 1), an alert to an admin user (deferred to item 38), and a way back for a fact that was moved (question 8, refused). Every other failure row of the spec names the slice that carries it — the save that fails in slice 3, the ambiguous name and the lapse in slice 4, the failed apply and the misread agreement in slice 5, the count in slice 1, the similar instruction in slice 9, the unrequested review in slice 6 — and two are marked invisible on purpose and no slice claims them: a reply that claims a save that did not happen, rested on AC2, and F6 finding nothing to move, which slice 6 answers in words but does not instrument.
- **One question is still unanswered and does not block this list.** Since plan D12, consent in this item is the model's reading of the user's words, as it already is for `remember_fact` and `update_profile` — but here the code checks the owner, the turn, the round and the attachment before applying, and for those two older tools nothing does. Whether they gain the same checks is not in 35q's scope and was never decided; it belongs to a roadmap item of its own.
