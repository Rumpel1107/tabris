## Notes

- **Slices 1 to 5 are what answers DEF-15**, and they are a shippable set on their own: after slice 5 an instruction lives where no merge can reach it, weighs above the facts, and the user is told when one is created. Slices 6 to 10 are the negotiation half — changing, removing, and moving what is already stored as a fact. The item is not closed at slice 5, but a tag can be cut there if anything interrupts the round.
- **Slice 1 is the riskiest and the only one that touches rows that already exist.** The shared counter changes how `save_fact` gets its id — the number now comes from `memory_ids` rather than from the facts table's own autoincrement, and the seed must be read from the production database's real maximum before the first save. If the counter and the rendering together exceed 200 lines once written, the split decided here is: the store plus the counter plus the recital first, then the system-prompt block, which is already slice 2.
- **Slice 2 measures before it builds, and so does slice 3.** The plan's own risk section says F1 and F2 recognition is unmeasured: the probe measured the review of stored rows, not the turn. Slice 3's probe is the one that can change the plan — if the `general` roster rarely calls `save_instruction` on real instruction-shaped messages, F1 shrinks to what slice 4's distillation catches, and the announcement of slice 5 becomes the main way a user learns anything was saved. That is why the two probes come before their code and not after.
- **Slice 7 is the first thing in the project that depends on Discord's message components**, which is why slice 6 proves the whole life cycle through the CLI's typed yes first. If the buttons turn out not to survive a restart the way plan D7 expects, what changes is slice 7, not the six before it.
- **Slices 9 and 10 are split on the mixed rows on purpose.** The whole-row copy is exact and needs no model beyond the classification; the split needs a second call and is the one place a part can be dropped. Keeping them apart means the owner can move his four instruction rows without exposing the four mixed ones to a split in the same change.
- `probe_kind.py` is not committed: it lives in a session scratchpad outside the repository, which is cleared without notice. Slice 9 is what gives it a home in `tools/`, beside `probe_freshness.py`; slice 3 needs it earlier, so slice 3 is what commits it — a measured prompt that exists only in a temporary directory cannot be the one production runs.
- **Read against the other phase documents.** The spec's twelve acceptance criteria all have a slice, and the plan's coverage table is the map this list follows. Three things the spec resolved are deliberately absent from every slice: a cap on how many instructions a user may hold (question 7, deferred — what ships is the count and the warning of slice 4), an alert to an admin user (deferred to item 38), and a way back for a fact that was moved (question 8, refused). Two failure rows are marked invisible on purpose in the spec and no slice claims them: a reply that claims a save that did not happen, rested on AC2, and F6 finding nothing to move, which slice 9 answers in words but does not instrument.
- **One question is still unanswered and does not block this list.** The consent of `remember_fact` and `update_profile` lives only in each tool's description — an instruction to the model, not a fence in code — while every applying step in this item is code (plan D9's "why"). Whether those two older tools should be brought to the same standard is not in 35q's scope and was never decided; it belongs to a roadmap item of its own.
